# ペルソナ・正解データセット作成プレイブック

実在アニメ・漫画等のキャラクターのペルソナ JSON と、参照付き Judge 用の正解データセットを
「低工数・高品質」で作るための方法論。パイロットキャラ 1 体（劇場アニメ 1 本、正解ペア 49 件 +
知識クイズ 10 問）の実制作と、外部リサーチ（先行研究調査。末尾「参考文献」）の検証結果に基づく。

**大原則（再掲）**: 実キャラのペルソナ JSON・原作セリフ・データセットは GitHub にコミットしない。
`personas/private/` と `scripts/eval/datasets/`（example を除く）は gitignore 済み。
ドキュメント・コミットメッセージでもキャラ名・作品名は匿名化する。

## 全体フロー

```
Step 0  時点決定（point_in_time）
Step 1  原作セリフの収集・加工（外部 AI へ切り出し可）
Step 2  ペルソナ JSON の設計・調整
Step 3  正解データセットのドラフト生成（エージェント）
Step 4  人間監修（1 件ずつ・全件必須）★最重要
Step 5  lint + 縮小スモーク評価
Step 6  DB 反映（persona:push）とベースライン取得
```

## Step 0: 時点決定（point_in_time）

複数作品・長期シリーズに登場するキャラは、**最初に「どの時点の人物か」を 1 つ決める**。
ここが曖昧なままだと、ペルソナ・会話例・データセット・クイズの間で時間軸が矛盾し、
評価が意味をなさなくなる。

- `identity.point_in_time` に時点を明記する（例:「◯◯（作品名）の時点。◯◯という立場」）
- **データセット・クイズも同じ時点に統一する**。乗機・所属・肩書き・関係者の生死は
  すべてこの時点基準
- 過去作由来の決め台詞・出来事は「本人の記憶・来歴」としてペルソナに残してよい。
  ただし発話例は現在時点の文脈に調整する
- 判定基準: 作中で人格・立場・関係性が大きく変わるキャラは時点統一が必須。
  変わらないキャラ（サザエさん型）は 1 ペルソナでよい

**知見（先行研究と一致）**: 長期シリーズのキャラは静的ペルソナでは破綻しやすい。
ArcANE（2026）は、物語のフェーズ（Character Arc）で条件付けする方式が全モデルで最良と報告。
将来複数時点を扱う場合は「Core Persona（不変の核）+ 時点別 State（関係性・知識境界・口調差分）」
の分離が有望（本プロジェクトでは将来拡張。単一時点統一が現行方式）。

## Step 1: 原作セリフの収集・加工

### 選定規則

- **問答として成立するやり取りだけを採る**。相槌のみ・叫び声・音声演出は採らない
- 独白は「〜の独白」と situation に書けば有効な評価ペアになる（捨てなくてよい）
- **設定説明の多い長文（演説・訓示の全文等）は評価素材に不適**。ペルソナ単体では
  再現不能で毎回不合格になるだけ。採るなら思想の核・骨格に短縮する
- 話者が台本上明記されていても、**宛先（誰に向けた発話か）の自動判定は信用しない**。
  先行研究では LLM の宛先同定はチャンスレベル近辺の報告もある。人手確認を前提にする

### プロンプトテンプレート 1: シーン抽出（外部 AI チャット用）

全セリフ集から対象キャラのシーンを分離し、ラベルを付ける工程。外部 AI チャット
（ChatGPT 等）に切り出せる。以下を貼り付けて使う:

```
あなたは脚本コーパスの整理者です。以下の全セリフ集から、キャラ「{キャラ名}」が
発話するシーンだけを抽出し、シーンごとに次の形式で出力してください。

## scene_{連番}: {シーンの一行要約}
- 場所・状況: {どこで何が起きているか}
- 対話相手: {相手キャラ名。独白なら「独白」、複数人なら列挙}
- 感情文脈: {このシーンでの対象キャラの感情状態}
- セリフ（発話順）:
  - {話者}: {セリフ}
- ラベル: {以下から該当するものすべて}
  - dialogue: 相手のいる問答として成立
  - monologue: 独白
  - speech: 演説・訓示（一対多）
  - combat: 戦闘中の音声
  - non_qa: 相槌・叫びのみで問答不成立

注意:
- セリフは一字一句原文のまま。要約・改変しない
- 対話相手が不明確な発話は「宛先不明」と明記する（推測で断定しない）
- 対象キャラが登場しないシーンは出力しない
```

### プロンプトテンプレート 2: 正解ペアドラフト生成

シーン別セリフとペルソナ JSON から referencePairs のドラフトを作る工程。
選定規則をプロンプト側に埋め込み、確信度で人手確認対象を仕分ける:

```
あなたはキャラクター評価データセットの作成者です。以下のシーン別セリフ集と
ペルソナ定義から、参照付き評価用の「状況→模範応答」ペアのドラフトを作ってください。

出力形式（1 ペアごと）:
{
  "situation": "誰が・どんな感情文脈で・何を言った/何が起きたか（特殊な状況なら必ず明記）",
  "reference": "原作セリフそのまま、または思想の核を保った短縮",
  "canon": true,
  "notes": "採用理由と、応答に含まれるべき要素（人間レビュー用）",
  "confidence": 0.0〜1.0,
  "exclusion_reason": null または除外すべき理由
}

規則:
- dialogue / monologue ラベルのシーンだけから作る（monologue は situation に「〜の独白」と書く）
- speech は全文を使わない。使う場合は思想の骨格に短縮し、その旨を notes に書く
- 宛先不明の発話は confidence を 0.5 以下にする
- 状況が特殊（極限状態・特定の相手にだけ見せる顔・非戦闘時等）なら situation に必ず書く
- 原文を一字一句変えない場合のみ canon: true。文脈調整したら notes に明記
- confidence 0.75 未満は人手確認必須としてマークする
```

**知見（先行研究と一致）**: 高精度候補抽出 → LLM ラベル → 人手レビューの半自動化が現実的。
LLM 全自動の話者・宛先同定は fine-tuned モデルに大きく劣る報告がある。
gold（評価データ）にするものは precision 重視で少数精鋭にし、recall は後から増やす。

## Step 2: ペルソナ JSON の設計・調整

- `identity.point_in_time` / `user_role` / `relationships` / `anti_examples` を活用する
- `user_role`（ユーザーをどういう立場として扱うか）を決めると、canon:false ペアの
  態度設計が一貫する（例:「側近の若い士官」なら助言はするが慰めない、等）
- `relationships` には主要関係者への**呼び方と態度**を書く。相手によって口調・開示度が
  変わるキャラでは特に効く（例: 側近にだけ漏らす弱音、特定人物への執着）
- **固定の会話例（few-shot）は 4〜8 件が目安**。口調代表例＋感情別（怒り・拒否・
  内省等）＋関係性別で構成する。8 件超の大量投入は慎重に（先行研究では例の過剰投入で
  性能が下がるケースの報告あり。増やすなら将来的には検索型に回す）
- 会話例に使ったやり取りは、**評価データセットの参照ペアと完全分離**する
  （同じものを両方に入れると自己参照で評価が甘くなる）

## Step 3〜4: 正解データセットの作成と人間監修

### 構成の目安

| 区分 | 比率 | 内容 |
| --- | --- | --- |
| canon:true（原作由来） | 6〜7 割 | 問答成立するやり取り。独白・短縮した演説骨格を含む |
| canon:false（原作にない状況） | **3〜4 割** | 日常・相談・挑発・政治問答等。過適合防止の要 |

- 件数: v1 は 20〜50 件。**本番回帰評価は 50 件以上を推奨**（先行研究ベンチマークの
  相場: CharacterEval 約 59 件/キャラ、PersonaGym 50 問/ペルソナ）
- canon:false は感情軸をカバーする: 平常 / 演説 / 劣勢 / 挑発された時 /
  特別な相手に関する話題 / 政治・思想問答 / 日常雑談 / 内省
- **notes は人間レビュー用**であり Judge には送られない。応答に含まれるべき要素・
  避けるべき要素・確立した原則を書き残す場所として使う（次キャラへの引き継ぎ資産になる）
- 運用: 失敗ログ（評価で見つかった弱点）から定期的に 10〜20 件追加し、評価セットを育てる

### 人間監修の進め方

**全件・1 件ずつ・人間が確認する。ここは省略しない。** パイロットでは
エージェントのドラフト 50 件のうち、人間の修正が入ったのは約 4 割
（削除 1・全面書き直し十数件・部分修正多数）。ドラフトの「もっともらしさ」は
高いため、まとめ読みでは違和感を素通りしやすい。1 件ずつが確実。

監修時のチェック観点（パイロットで確立した執筆原則）:

1. **situation に文脈が書けているか**: 誰が・どんな感情文脈で・特殊な状況か。
   特殊状況（極限状態・近い距離の相手にだけ見せる顔・非戦闘時等）のペアは、
   situation に特殊文脈を明記しないと汎化がゆがむ
2. **決め台詞は 1 応答 1 つまで**: 2 つ連続は「名言集」化し、自然な会話でなくなる
3. **記号性の強い有名台詞を canon:false で原文使用しない**: 文脈が合っていても
   ファンサービス回収に見える。**同じ精神を別の言葉で言い直す**
4. **過去作の台詞を無関係な文脈で回収しない**: キャラ本人は自分の過去発言を
   引用グセとして持っていない（そういうキャラでない限り）
5. **キャラの核心的な告白を通常会話でさせない**: 原作で極限状況（死の間際・
   特別な相手との対決等）でのみ出た本音は、その条件が揃わない限り出さない。
   通常会話ではぼかす・怒りや冷たさで覆う
6. **私的動機を公的論理で覆うキャラは、その構造を崩さない**: 素直な弱さの告白・
   明晰すぎる自己分析・自己憐憫は、キャラの防衛機制を壊す。演説は大義の建前を保つ
7. **「良識ある大人」化に注意**: ドラフトは慰め・免罪・寛容な助言に流れやすい。
   キャラ固有の冷たさ・皮肉・突き放しを保つ
8. **現代的・倫理的な語彙に注意**: 「幸福」「資格」等の説明的な語より、
   キャラの世界観の語彙（そのキャラなら何と呼ぶか）で言い換える
9. **相手（user_role）との距離感で応答を条件付ける**: 同じ質問でも一般人と側近では
   応答が違う。notes にどの関係性を想定したか書く
10. **短い名返答は正当**: canon:true では situation が文脈を担い、reference が
    一言でも成立する。無理に膨らまさない

### 参照過適合の防止

- canon:false を 3〜4 割確保する（上表）
- few-shot 会話例と評価用参照ペアを完全分離する（Step 2 参照）
- クイズに**時間軸カナリア**を仕込む: 時点（point_in_time）とズレた知識・振る舞いを
  検出する設問（例: 現在の乗機・立場を問う。過去時点の答えを返したら時点統一が
  効いていない証拠）。パイロットのスモークでも実際に時間軸ズレを 1 件検出した

## Step 5: lint とスモーク評価

```bash
# 形式検証 + 品質ルール（警告のみ。推奨値の根拠は本ドキュメント）
npm run dataset:lint -- scripts/eval/datasets/<キャラid>.json

# 縮小スモーク（コスト $0.01 未満）: loadDataset 通過と refFidelity 出力を実確認
npm run eval -- --persona-file personas/private/<id>.json \
  --dataset scripts/eval/datasets/<キャラid>.json --scenarios 1 --max-turns 2
npm run eval:quiz -- --persona-file personas/private/<id>.json \
  --dataset scripts/eval/datasets/<キャラid>.json
```

- クイズの不正解は**まずベースラインとして受け止める**。キーワード側を安易に緩めない
  （「らしい」応答でも知識・時間軸が誤っていれば不正解が正しい）
- 判定キーワードの調整（表記ゆれ追加等）は、実際の応答を見てから最小限に行う

## Step 6: DB 反映とベースライン

```bash
# ローカル既定 DB へ
npm run persona:push -- --file personas/private/<id>.json
# 本番（リモート DB）へ。--yes 必須
npm run persona:push -- --file personas/private/<id>.json --yes
```

反映後、本評価（全シナリオ）を回してベースラインを保存し、以後の改善は
A/B（`eval:compare` / 回帰チェック）で測る。

## クイズ設計パターン

| 型 | 作り方 | 判定 |
| --- | --- | --- |
| 正答型 | 時点基準の基礎知識（本名・関係者・乗機・作戦・出自）を問う | `mustContain`（AND。要素内 `\|` 区切りで表記ゆれ OR） |
| 偽前提の訂正型 | わざと誤った前提で聞く（例: 敵対組織に所属していた、故人が存命） | 訂正に必要な語を `mustContain` に。**「違う」とだけ言って乗り切る回答は正答にしない**（訂正の中身まで要求する） |
| 捏造検出型 | 原作・ペルソナに情報がない具体値（人口・日付等）を問う | `mustContain: []` + `mustNotContain` に捏造しがちな表現。「知らない」と言えれば正答 |

- 10 問なら 正答型 7 / 偽前提・捏造検出型 3 が目安。捏造検出型（mustNotContain 使用）は
  最低 2 問（lint が警告する）
- `mustContain` の語は最小限に（固有名詞の核だけ。「フルネーム一致」等は要求しない）

## 工数目安と分業基準

パイロット実績（正解ペア 49 件 + クイズ 10 問、原作セリフ集は入手済みの前提）:

| 工程 | 主担当 | 実績・目安 |
| --- | --- | --- |
| シーン抽出・ラベル付け | 外部 AI チャットに切り出し可 | セリフ集の規模による（パイロットは人手併用） |
| ペルソナ調整（時点統一） | エージェント + 人間確認 | 1 時間程度 |
| データセットドラフト生成 | エージェント | 1〜2 時間 |
| **人間監修（1 件ずつ）** | **人間必須** | **1 件 2〜10 分 × 全件。パイロットは複数セッションに分割** |
| lint・スモーク・DB 反映 | エージェント | 30 分程度 |

- 外部 AI チャットに切り出してよい工程: シーン抽出、ドラフト叩き台、先行研究調査
- 人間監修必須の工程: 参照ペアの確定（キャラ解釈の最終判断）、クイズ判定基準の確定、
  本番 DB への反映判断

## 外部リサーチからの知見（検証済みの要点）

出典の実在・主要な数値は検証済み。個別の細かい実験数値は原典の本文由来で
アブストラクトからは未確認のものがある（方向性としては信頼可）。

1. **評価件数の相場**: 主要ベンチマークは 50〜60 件/キャラ程度。20〜50 件は MVP として
   妥当、本番回帰は 50 件下限が目安
2. **件数より層化**: 時点・関係性・知識境界・口調・未登場状況・拒否/知らない応答の
   カバレッジが件数より重要
3. **gold は単一正解文より許容条件**: 参照 1 文への一致でなく「◯◯に触れる・◯◯は
   出さない」等の条件化が過適合に強い（本プロジェクトでは将来課題。下記参照）
4. **few-shot の飽和**: 固定例は 4〜8 件目安。過剰投入で劣化するケースの報告あり。
   大量に効かせたい場合は入力ごとの検索型（RAG）が有望
5. **抽出の自動化限界**: 話者はともかく宛先同定は LLM 単体では不安定。
   人手レビュー前提の半自動化が現実的
6. **時点・Arc 管理**: 静的ペルソナは長期シリーズで破綻。Core + 時点別 State 分離が
   研究動向（ArcANE, CharacterGPT）
7. **ASR（セリフソースがない作品）**: Whisper 系 + VAD + 音楽分離 + 話者分離で
   下書きは作れるが、話者名の自動割当は保証されない。gold 化には人手確認必須。
   まず 10 分程度で誤字率・話者誤割当率・手修正時間を測って ROI を判断する

## 将来課題（今回スコープ外・記録のみ）

- **Judge 向け許容条件フィールド**: notes（人間用）とは別に、Judge に送る
  per-pair の許容条件・禁止事項（例:「正確な引用は要求しない」「未来知識を出したら減点」）。
  gold の条件化（知見 3）に対応する
- **メタデータスキーマ v2**: timeline_position / relationship_state / forbidden_facts /
  style_tags 等の構造化。現行は situation への文脈明記で代替
- **複数時点ペルソナ（Core + Arc State 分離）**: 同一キャラの時点別バージョン管理と、
  同じ質問を複数時点に投げる評価
- **検索型 few-shot（RAG）**: 入力ごとに近い原作発話を 3〜6 件検索して注入
- **few-shot 件数の飽和点実験**: ペルソナ説明のみ〜固定 8 件 + 検索 10 件までの
  ablation を参照付き Judge で測る（T3 の A/B 検証と親和性が高い）
- **ASR パイプライン実装**: 上記知見 7 の手順化
